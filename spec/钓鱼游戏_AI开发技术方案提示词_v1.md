# 2D 全球钓鱼旅行游戏：AI 开发技术方案提示词 v1.0

编写日期：2026-10-02  
用途：将本文件完整交给具备代码编辑、运行及必要素材制作能力的 AI，作为开发任务说明。  
游戏暂名：《远岸钓记》。名称可修改，不影响技术设计。

---

## 1. 你的任务与最终交付目标

请作为游戏开发者，依据以下需求，开发一款可以安装到安卓手机上游玩的 2D 休闲治愈钓鱼游戏。完成游戏工程、实际使用的美术与音效素材、离线存档、图鉴统计、安卓打包和验证。

收到本文件作为开发任务后，先检查工作环境并简述实施顺序，然后推进实际开发。分阶段交付可运行成果，直到约定范围完成。每个阶段都保留下一步可继续的工程和进度记录。

如用户明确要求只评审方案、只制作素材或暂缓编码，以用户当次要求为准。本文是可供后续执行的完整开发指令。

### 1.1 已经确认的核心需求

以下要求是产品的核心，不能擅自删减：

1. 游戏采用 **2D**，整体为休闲、治愈、旅行与收集体验。
2. 玩家能去不同水域钓鱼，海钓包含不同国家或地区的海域。
3. 鱼种丰富，不同水域和钓点有不同鱼群，也允许部分鱼种跨地区出现。
4. 同一种鱼有不同个体大小；长度、重量、视觉尺寸和溜鱼难度存在合理关联。
5. 鱼类美术采用 **接近真实鱼类的手绘插画**，保留各物种的体形、鱼鳍、嘴部和花纹特征。
6. 有完整的 **鱼类图鉴、收集进度和展示功能**。
7. 图鉴必须记录 **每种鱼在当前存档内累计成功钓获的数量**。
8. 钓获后出售或放生，不减少历史累计钓获数，不清除图鉴和个人纪录。
9. 钓鱼有可以感受到的抛竿、咬钩、提竿和溜鱼过程，鱼种之间有行为差异。
10. 最终提供能安装的安卓 APK，说明实际验证范围。

以下是方案默认值，并非用户已经逐项确认的硬性要求。除非发现明确冲突，直接按默认值推进；如果用户补充要求，调整相应部分即可。

| 项目 | 默认选择 |
| --- | --- |
| 游戏方式 | 单机、离线可玩、本地存档 |
| 语言 | 简体中文，使用能正确显示中文的授权字体 |
| 屏幕 | 竖屏，单手操作优先，逻辑设计尺寸约 720 × 1280 |

| 语言与渲染 | 使用类型标注的 GDScript，Compatibility 渲染模式 |
| 体验 | 普通鱼较宽容，大个体和少见鱼有更高挑战 |

## 2. 内容范围与分期

### 2.1 首个完整版本 V1 的默认交付范围

这是一套可调整的内容预算。请把它当作完整版本的工作范围，先完成小规模验证切片，再扩充到此范围。

| 水域 | 场景方向 | 至少两个可区别的钓点 |
| --- | --- | --- |
| 教学淡水湖 | 芦苇、木桥、树荫、柔和晨光 | 岸边浅水、较深的湖湾 |
| 日本近海 | 小渔港、灯塔、防波堤 | 港内码头、外侧礁岸 |
| 挪威峡湾 | 山体、木屋、开阔深水 | 岸边港湾、船钓点 |
| 地中海沿岸 | 海边建筑、岩岸、明亮海面 | 小码头、近岸船钓点 |

V1 的默认内容量：

- 4 处水域、至少 8 个钓点。
- 全局至少 **32 个不同的真实鱼种**；每处水域至少有 8 种可钓鱼，允许合理重叠。
- 物种数量按唯一 `species_id` 去重；大小、花色、重复条目不算新鱼种。
- 每个鱼种都有实际图像、资料、尺寸分布、出现条件、行为配置和图鉴记录能力。
- 至少 3 种可感知的挣扎行为组合，例如持续拉扯、短促冲刺、间歇休息。
- 3 档入门到进阶装备、至少 4 类有明确偏好的鱼饵。
- 有日间与黄昏等时间表现，以及至少两种可区分的天气表现。
- 日夜与天气使用游戏内时间，支持离线，不要求玩家在现实中的指定时间上线。
- 至少有一条完整的发现鱼种、获得奖励、升级装备、解锁新水域的成长路径。

具体鱼种名单必须先查证再确定。某个候选鱼不适合对应水域、岸钓方式或深度时，应替换候选鱼，不能为了凑数量随意放置。

### 2.2 验证切片与后续扩展

- 第一个技术切片：1 个钓点、4 种鱼，跑通钓获、统计、存档和安卓安装。
- 内容制作验证：2 处水域、约 12 种鱼，验证统一美术和批量配置流程。
- V1 完整版：达到上一节的 4 处水域、至少 32 个真实鱼种。
- 后续扩展方向：6—8 处水域、60—100 种鱼，可加入澳大利亚海域、热带海岛等目的地。

以上为不同阶段。技术切片完成时，报告该阶段完成；只有满足 V1 范围和验收条件，才能报告 V1 完成。首版架构需要能自然增加内容，但不提前制作复杂的通用编辑器或插件系统。

## 3. 游戏循环与钓鱼手感

### 3.1 主要循环

选择目的地 → 选择钓点与鱼饵 → 抛竿 → 观察浮漂 → 提竿 → 溜鱼 → 钓获结算 → 图鉴与纪录更新 → 出售或放生 → 装备改进与旅行解锁。

每次游玩几分钟也应有明确收获。优先做好发现新鱼、看到漂亮鱼身、刷新尺寸纪录和来到新地方的体验。

### 3.2 操作设计

- 抛竿：长按蓄力、松手投出，落点影响可触及的鱼群；入门阶段提供宽容的有效落点范围。
- 咬钩：通过浮漂、水纹、声音和可关闭的震动提供信号，区分轻微试探与正式咬钩。
- 提竿：给予普通鱼充足的反应窗口，特殊鱼可以更讲究时机。
- 溜鱼：按住收线，松手卸力；张力过高可能断线，长时间过松可能脱钩。
- 反馈：鱼竿弯曲、鱼线状态、水花、鱼的运动、声音共同表达状态，辅助张力条要清楚。
- 大鱼需要更多节奏判断；普通鱼适合短时间轻松游玩。

初始调校参考：大多数咬钩等待控制在数秒到十余秒，普通鱼溜鱼约 10—25 秒，较大个体适度延长。此处是可调整的体验目标，不是模拟真实钓鱼的时间尺度。

### 3.3 状态与中断

明确管理选点、抛竿、等待、咬钩、提竿、溜鱼、成功结算、逃脱和暂停等状态。状态转换必须可追踪，输入只影响当前允许的动作。

- 每次抛竿创建唯一的钓鱼会话；已经生成的鱼不能因暂停、打开界面或恢复前台而重抽。
- 成功钓获和逃脱互斥；旧会话的延迟回调不能影响新一轮。
- 触控取消、手指移出、应用失焦时不能留下持续收线的卡死状态。
- 打开系统界面、应用进入后台时暂停鱼的行为、张力变化、声音和震动。
- 恢复后先处于暂停状态，玩家确认继续操作后恢复溜鱼。
- 首版无需保存整段溜鱼物理状态。进程被终止后可以结束尚未完成的本轮，并回到钓点；已经保存的钓获必须保留。

## 4. 鱼种、出现条件与个体大小

### 4.1 区分物种定义与钓获个体

物种定义描述某种鱼的共同属性；钓获个体描述这一次遇到的具体鱼。两者分别建模。

| 物种定义 | 钓获个体 |
| --- | --- |
| 稳定的 species_id、中文名、学名 | 唯一 catch_id 与所属会话 |
| 美术资源与识别特征 | 实际长度与重量 |
| 栖息水域、盐度、深度、出现权重 | 本次钓获的水域与钓点 |
| 鱼饵偏好与游戏内时间/天气权重 | 本次时间、天气、装备快照 |
| 体型范围、长度重量关联规则 | 大小等级、当前行为参数 |
| 挣扎行为配置 | 是否新发现、是否刷新纪录 |
| 资料来源与核查状态 | 出售或放生等后续处理状态 |

每个条目使用明确的物种身份。宽泛名称如“鲷鱼”“石斑鱼”可以作为分类，但不能作为含糊混合多种鱼的最终物种条目。

### 4.2 遭遇生成

先根据水域、钓点、生境、盐度、深度和装备可达性筛选候选鱼，再根据鱼饵、时间、天气及基础权重抽取鱼种，最后生成具体个体。

- 现实分布资料与游戏调校参数分别记录。
- 鱼的国家或海域分布应有依据；不要把国家标签当作生物分布边界。
- 特定时间、天气、稀有度和难度可以做游戏化设计，但不要冒充未经核实的生物学事实。
- 开发阶段允许注入随机种子，使抽样与失败能复现；正常游玩采用变化的随机序列。
- 候选集合为空时给出合理提示或明确的保底设计，不偷偷生成不属于该水域的鱼。
- 图鉴里标为可收集的鱼必须有实际可达的出现途径。

### 4.3 大小与重量

- 每个鱼种使用自己的尺寸范围和分布，大个体相对少见，不能所有鱼共享一个随意的重量区间。
- 长度和重量必须有关联，不能分别独立均匀抽取。
- 有可靠的物种长度重量关系时，可以使用相应模型，并明确长度类型与单位。
- 缺少可靠系数时，采用有依据的尺寸锚点与温和体况变化构造游戏数值，标注其为调校参数，不编造科研系数。
- 存档可统一以整数毫米和整数克保存，界面转换为厘米、米或千克，避免显示舍入与纪录比较不一致。
- 小、标准、大、巨物等等级按同一物种的区间判断；稀有鱼种和罕见大个体是两个不同维度。
- 个体大小影响拉力、耐力、短时冲刺和展示尺度，同时限制整体难度，避免只靠等待很久体现大鱼。
- 钓获展示需要让尺寸差异可感知；图鉴大图可自动适配版面，但应展示清楚的长度和比例参照。

## 5. 图鉴、收集统计与展示

图鉴是核心系统，需要从第一版技术切片就接入真实钓获流程。

### 5.1 图鉴列表

- 展示已发现物种数、当前版本可收集物种数和收集进度。
- 已解锁条目显示清楚的鱼类缩略图、名称、累计钓获数。
- 未解锁条目显示剪影和适量寻找提示，避免完全没有行动线索。
- 支持按水域、已发现/未发现筛选，以及按名称或钓获数量排序。
- 有可读的中文搜索；手机上输入与筛选不遮住主要内容。
- 收集进度按唯一物种计算；同一种鱼在多个海域出现也只算一种。
- 只把当前版本实际可获得的物种纳入分母，未来规划内容不阻止当前版本达成收集目标。

### 5.2 物种详情

每种鱼至少展示：

1. 接近真实的高清手绘插画，可放大查看。
2. 中文名、学名、简短介绍。
3. 可以钓到的地区、钓点线索和鱼饵提示。
4. 当前存档内累计成功钓获数量。
5. 首次钓获的时间、地区和钓点。
6. 最近一次钓获信息。
7. 历史最大长度，以及对应个体的重量、钓点和时间。
8. 历史最大重量，以及对应个体的长度、钓点和时间。

最大长度和最大重量可能来自不同个体，分别保存完整的纪录快照。不要把两个最大值拼成一条从未钓到过的鱼。

### 5.3 钓获展示

钓获后呈现鱼身、名字、长度、重量、地点，并明确标记首次发现或刷新纪录。允许收藏该物种或将某条纪录设为展示项。

提供简洁的“我的收藏”展示页，默认可展示 6 个喜欢的鱼种或真实钓获纪录。展示项是对物种或纪录的引用，不再创建钓获事件，不增加统计。首版不要求复杂的可经营水族馆。

### 5.4 累计数量的明确语义

- 一条鱼被成功拉上岸，并完成一次有效钓获结算后，对应 `catch_count` 增加 1。
- 咬钩、提竿成功但最终逃脱、预览鱼种、打开图鉴、展示收藏都不增加数量。
- 出售或放生不扣减历史累计数量。
- 重复点击、重复回调、重新打开结算页、保存重试不能重复计数或重复发奖励。
- 同种鱼在不同地区钓到，累计到同一物种的全局数量；同时可记录按地区的分项数量。
- 全局累计钓获数由物种统计求和得到，避免维护两份可能不一致的总数。
- 游戏更新和存档迁移必须保留已解锁物种、累计数量和纪录。

该统计指当前本地存档。卸载、清除应用数据或主动新建存档后的跨安装保留，不属于首版保证；不要让界面暗示其是云端永久记录。

## 6. 成长、装备与旅行

- 基础装备和基础鱼饵允许玩家持续游玩，避免货币耗尽后无法钓鱼。
- 收入来自明确的钓获奖励或出售收益；同一事件只结算一次。
- 放生也应保留图鉴和历史纪录，可提供温和的成长奖励，但避免重复结算获利。
- 装备影响可应对的鱼、抛竿范围和容错度，不能替代玩家所有操作。
- 地区解锁可结合发现物种数和合理旅行费用；确保资源获取路径不存在循环锁定。
- 在普通鱼、较大个体、稀有物种之间分配不同目标，避免所有成长都由低概率抽取决定。
- 不设置必须每天上线的签到链、等待现实数小时的体力恢复或强制广告。

## 7. 技术路线与职责划分

### 7.1 固定技术路线

- 使用 **Godot 4.x 官方稳定版 + GDScript + 2D 场景**。
- 开工时核查官方版本与导出要求，记录具体引擎版本，导出模板必须匹配该版本。
- 使用 Compatibility 作为首版渲染方案，水面效果以轻量的 2D 实现为主。渲染功能边界参考 [Godot 渲染模式说明](https://docs.godotengine.org/en/stable/tutorials/rendering/renderers.html)。
- 场景与界面使用 Godot 的节点、场景、Control 布局、动画与音频能力。
- 首版不依赖在线服务、实时生成模型或外部网页来完成游戏主循环。
- 不为本项目额外引入 C#、Node 后端、账号数据库或 WebView 游戏容器，除非用户明确改变目标。

### 7.2 静态内容与运行状态

鱼种、地区、钓点、装备和鱼饵，使用项目内 JSON 作为统一的可编辑内容来源。加载时转换成结构明确的 GDScript 数据对象并校验。场景、纹理、音频按 Godot 常规资源方式管理。

不要同时维护内容完全重复、需要手工同步的 JSON 和另一套鱼种表。引擎导出配置需要确保 JSON、字体、纹理和音频全部进入 APK。

运行中把静态定义视为只读。个体状态、玩家统计、装备拥有情况和地图解锁保存在独立状态中。

### 7.3 建议模块

| 模块 | 主要职责 |
| --- | --- |
| 内容目录 | 加载鱼种、水域、钓点、装备，验证 ID 与资源引用 |
| 地区与场景 | 切换钓点、管理时间天气、加载和释放地区资源 |
| 遭遇生成 | 筛选候选鱼、抽取物种、生成长度重量与行为参数 |
| 钓鱼会话 | 输入、状态转换、溜鱼张力、鱼的行为、暂停恢复 |
| 钓获结算 | 接收唯一结果，更新统计、纪录与奖励，处理出售/放生 |
| 图鉴与收藏 | 查询、筛选和展示玩家真实数据 |
| 存档 | 单一写入口、版本迁移、备份恢复、失败反馈 |
| 音频与触觉 | 环境音、反馈音、音量设置、可关闭震动 |

通过清楚的接口和必要的信号连接模块。避免把鱼种数据、战斗逻辑、界面和文件写入全部堆进一个脚本，也避免搭建超出本游戏需要的通用框架。

### 7.4 数据契约

| 数据类型 | 至少需要的内容 |
| --- | --- |
| FishSpecies | species_id、名称与学名、美术路径、形态信息、尺寸模型、行为、资料来源 |
| Region | region_id、名称、国家/海域说明、场景资源、钓点集合、解锁条件 |
| FishingSpot | spot_id、region_id、生境、盐度、深度/可达性、遭遇表 |
| EncounterEntry | species_id、基础权重、鱼饵/时间/天气修正、条件限制 |
| Equipment / Bait | 稳定 ID、效果参数、获取条件、价格或补给规则 |
| CatchRecord | catch_id、species_id、长度、重量、地区、钓点、时间及处理状态 |
| SpeciesStats | catch_count、首次/最近钓获、最大长度纪录、最大重量纪录、地区分项 |
| PlayerSave | schema_version、物种统计、收藏、装备、货币、解锁、设置、必要的去重状态 |

ID 使用稳定的 ASCII 标识，与显示名称分离。重命名中文名称不能让玩家丢失纪录。数据校验至少覆盖重复 ID、失效引用、缺失资源、负权重、空候选集、不合法尺寸和不可达解锁条件。

## 8. 美术素材制作方案

### 8.1 统一风格

鱼：真实比例与形态基础上的精细手绘插画，适度柔化色彩，轮廓清楚，鱼鳍与花纹可辨。保持正常鱼眼和解剖结构。

场景：柔和的旅行插画，有地区识别度、明确前后层次和适合长时间观看的水面。游戏首屏突出风景、浮漂与钓鱼操作。

界面：以旅行手册和自然图鉴的气质组织，文字清晰、操作简洁。不要用大量企业后台式卡片、夸张渐变和装饰数字占据游戏画面。

### 8.2 鱼类插画生产流程

1. 为物种建立资料卡：学名、中文名、关键识别特征、形态参考、合理尺寸和资料来源。
2. 查阅可信的物种数据库、水产或海洋研究机构、博物馆资料，核对学名、形态与地域分布。图片是否可复用单独确认，公开可访问不自动代表可商用。
3. 先选择 4 种轮廓明显不同的鱼生成风格样张，统一侧面视角、朝向、光照、质感和留白。
4. 在同一套风格规范下逐种生成。需要保持一致时提供已选样张作为风格参考，物种照片或资料图作为形态参考，并区分两类参考用途。
5. 逐条检查鱼鳍、尾部、嘴部、斑纹和整体形状。生图输出未经校对不能当作准确的物种插图。
6. 修正局部错误，检查完整轮廓与真实透明通道，整理为游戏纹理、展示大图和缩略图。
7. 在游戏的实际缩放、深浅背景和手机尺寸下复核。

优先使用执行环境已经提供的图像生成工具。支持真实透明背景时启用透明输出，并保留 Alpha 通道。不要把画出来的棋盘格当作透明背景。

如果当前 AI 没有生图工具，先完成可以独立推进的工程和素材清单，提供逐资产的生成提示词与接入位置，明确缺失状态。不能把临时占位图描述成最终真实鱼类插画。新增收费 API、账号或密钥需求须由用户授权，不能静默切换到付费路径。

### 8.3 可复用的单鱼生成提示词模板

```text
用途：2D 安卓钓鱼游戏中的鱼类图鉴插画与钓获展示素材。
主体：一条完整的【中文名称】，学名【学名】。
形态依据：【写入已核查的体形、嘴部、背鳍、胸鳍、尾鳍、斑纹等关键特征】。
风格：接近真实鱼类的精细手绘自然插画，轻微纸笔或绘画质感，适合治愈旅行游戏。
构图：严格侧面，朝左，鱼身自然舒展，完整鱼鳍和尾部均在画面内，四周保留安全留白。
光照：柔和的左上方光照，与已提供的风格样张一致。
背景：真实透明背景，输出保留透明通道。
限制：仅一条鱼，无水面、无钓钩、无文字、无标牌、无边框、无地面投影。
准确性：保留该物种的正常眼睛、真实比例和关键形态，避免额外鱼鳍、断尾和错误花纹。
参考图角色：物种参考用于形态；风格样张用于笔触、色彩和光照，不混淆物种。
```

模板中的特征必须替换为该鱼种的资料，不能把占位文字直接用于批量生成。实际输出能力、尺寸和参数以当前工具为准。

### 8.4 动画与资源复用

- 每种鱼至少有独立且可辨认的主插画；允许同一种鱼在多个地区复用素材。
- 水下使用鱼影、运动轨迹、水花与少量细节来表达状态。
- 钓获展示使用主插画、轻微身体弯曲、尾部和鱼鳍运动。
- 对适合拆分的物种拆分鱼身、尾部、鱼鳍，使用简单骨骼或局部形变；保留各部分的连接重叠区。
- 扁平鱼、细长鱼等特殊体形可以使用不同动画模板，避免强行套用同一轮廓。
- 不要求生图模型一次产生无错位的整套动画帧；用固定底图与引擎动画保持形态稳定。
- 同种鱼不同大小主要复用素材并调整个体尺度和参数，必要时增加少量合理外观变化。

### 8.5 场景生产

按远景、岸边主体、前景植物、水面和交互物分层。天空、山体、建筑和植物可由生图制作，水纹、波光、浮漂、鱼线、水花和天气由引擎动态表现。

生成分层图片时保持相同地平线、视角和光照。共享区域的钓点可以复用部分远景，但岸线构图、前景和玩法条件必须可区分。不要把整张带水面的背景在物体后面直接平移来模拟水流。

场景提示词结构：

```text
用途：2D 竖屏休闲钓鱼游戏的【指定场景图层】。
地点：【具体海域与钓点类型】，地区线索为【已核查且适合该地点的建筑/地貌/植被】。
风格：与既有场景保持一致的柔和手绘旅行插画。
构图：与场景设计稿保持同一视角和地平线；为水面、浮漂与手机操作区域留出空间。
光照与时间：【日间/黄昏等确定条件】。
本次只生成：【远景/岸边/前景植物等明确对象】，需要叠加时使用真实透明背景。
不包含：游戏按钮、文字、统计面板、已由其他图层负责的物体。
```

### 8.6 素材记录与预算

- 保存素材清单，记录 asset_id、用途、路径、尺寸、来源或生成方式、生成提示词、参考资料、许可状态、审核状态和实际使用位置。
- 最终素材放入项目内，不能依赖生成工具的临时目录或外部图片链接。
- 高清工作底稿与运行时纹理分开管理；按实际显示尺寸导出，图鉴缩略图单独制作。
- 不为每个列表条目常驻加载高清鱼图；详情页按需加载，地区切换释放不再使用的大纹理。
- 音效与环境音使用可说明来源的自制、生成或获授权素材，调节音量并处理循环接缝。
- 字体、第三方组件和素材保留必要署名与许可说明。生成来源本身不等于已经解决所有授权问题。

## 9. 钓获结算与本地存档

### 9.1 结算由单一入口负责

一次有效钓获的物种统计、纪录、奖励及必要的待处理鱼记录，在同一份状态更新中完成，并以一个存档事务提交。界面只展示结算结果，不各自修改统计或货币。

建议顺序：

1. 当前钓鱼会话生成唯一 catch_id，并进入只能结算一次的终态。
2. 结算服务检查会话身份和 catch_id，拒绝旧回调与重复请求。
3. 构造新的玩家状态，更新数量、纪录、图鉴和一次性奖励。
4. 持久化新状态与去重信息。
5. 保存成功后显示已保存的钓获结果。
6. 出售或放生作为幂等的后续操作，只处理该记录一次，不再增加钓获数。

保存失败时保留待处理结果并允许重试，清楚提示玩家，不伪装为已经成功保存。不要无限增长完整钓获事件日志；对近期去重和待处理记录设置合理上限，并确保超出记录窗口的旧会话事件根本不能重新进入结算。

### 9.2 存档实现要求

采用带 schema_version 的本地 JSON 存档，存放在 Godot 的 user://。API 与序列化基础参考 [Godot 存档文档](https://docs.godotengine.org/en/stable/tutorials/io/saving_games.html)；下列可靠性要求属于本项目的额外设计要求。

- 所有写入经过同一个存档模块，串行处理，避免多个界面同时覆盖文件。
- 使用同目录临时文件、写入完成与关闭、内容校验、保留有效备份、替换正式文件的流程。
- 检查每一步的返回值，结合目标平台核查替换行为；不能未经验证就声称拥有跨平台的原子性保证。
- 主文件损坏时尝试有效备份；两者都失败时保留损坏文件并说明情况，不静默清空玩家纪录。
- 新字段有默认值；旧版本有可验证的迁移步骤；遇到未知的更高版本存档时保护原文件，避免降级覆盖。
- 捕获成功、出售/放生、购买、解锁和收藏变化等关键事件保存；不能仅依赖退出游戏时保存。
- 应用进入后台时保存已有稳定状态；移动系统终止进程后不应依赖退出回调补救。
- 读取和重建状态时不重放“成功钓获”奖励，不再次增加统计。
- 存档不保存任意可执行场景路径或加载外部脚本。

初版无需服务器、云同步或防作弊系统。开发调试入口不得默认暴露在面向玩家的发行版本里。

## 10. 界面与安卓体验

需要的主要界面：

1. 启动/继续游戏与基础设置。
2. 旅行目的地与钓点选择。
3. 主钓鱼画面。
4. 钓获结果与出售/放生。
5. 图鉴列表和鱼种详情。
6. 我的收藏展示。
7. 简洁的装备与鱼饵选择。

旅行界面可以使用目的地插画与路线关系来呈现，不必为了视觉效果额外实现复杂地理地图。

手机适配要求：

- 使用容器、锚点和安全区域布局，适配刘海、挖孔、手势导航区和较长屏幕。
- 控件可触摸，主要收线操作位于容易触及的区域，关键点击区域约 48 dp 或更大。
- 字体可读，不能仅以颜色区分危险、成功和稀有状态。
- 系统返回键按层级关闭弹窗、返回界面；溜鱼时返回应先暂停。
- 支持音量和震动开关，恢复前台后设置保持。
- 暂定以目标中档安卓手机稳定 30 FPS 为验收基线，60 FPS 为优化目标；指定设备前不做普遍性能承诺。
- 检查载入时长、场景切换、图鉴翻页的内存变化和持续游玩发热；发现异常后按实测优化。
- 对水面纹理、粒子、透明叠加和高分辨率图鉴资源设置预算，限制同时存在的效果数量。

## 11. 安卓构建与安装交付

尽早打通安卓导出，在技术切片阶段就验证安装和触控。

- 依据锁定引擎版本的 [Godot 安卓导出文档](https://docs.godotengine.org/en/stable/tutorials/export/exporting_for_android.html)，确认匹配的导出模板、JDK、Android SDK 及该构建方式需要的其他依赖。
- 将精确工具版本、导出步骤和运行条件写入构建说明，避免依赖某台机器上的未记录设置。
- 优先交付 arm64 的签名发行 APK，早期调试包明确标注为 debug。
- 设置稳定包名、应用名、图标和版本号；后续更新保持相同包名与签名身份。
- 按 [Android 应用签名文档](https://developer.android.com/studio/publish/app-signing) 管理签名。签名密钥和密码放在安全的本地位置或环境配置中，不进入代码仓库、源码压缩包或公开日志。
- 若需要创建本项目的新签名密钥，说明保管位置和后续更新对它的依赖，不把密钥内容或密码输出到聊天。
- APK 包含离线需要的全部素材和数据，不在首次进入游戏时依赖网络下载。
- 检查包内 ABI、权限、版本信息及资源，游戏功能不需要的敏感权限不申请。
- 首版交付目标是 APK 直接安装。若以后上架 Google Play，再核对当时的 AAB、目标 SDK 和商店要求。
- 在目标手机上检查来源安装权限与设备限制，不能假设所有安卓设备的安装流程一致。

没有连接真机时，仍应完成能独立完成的工程、构建和模拟器验证，并明确标记真机验收待完成。构建成功、模拟器通过、真机通过是不同证据，分别报告。

## 12. 执行顺序与每阶段产物

### 阶段 A：环境与可运行骨架

检查现有工程和指令；锁定引擎与导出依赖；创建项目、基础场景、输入与本地存档骨架。尽早产出能启动的 Android 测试包。

产物：可打开工程、工具版本记录、基础构建说明、启动验证结果。

### 阶段 B：一轮完整钓鱼与统计

完成 1 个钓点、4 种鱼的技术切片，跑通真实输入、成功/失败、结算、累计数量、长度重量纪录和重启恢复。

产物：可以反复游玩的核心循环、基础图鉴、实际保存与恢复的验证记录。

### 阶段 C：美术与内容流程

建立鱼种资料、统一风格样张、分层场景与素材清单。扩充至 2 处水域和约 12 种鱼，完成接近最终画面的移动端展示，验证鱼影、主插画、缩略图与简单动画的复用。

产物：已接入的实际美术、来源与提示词记录、可在手机尺寸下检查的界面。

### 阶段 D：完成 V1 内容

扩充到 4 处水域、至少 8 个钓点和至少 32 个去重真实鱼种，完善图鉴、收藏、装备、鱼饵、地区解锁与天气时间表现。

产物：完整内容清单、所有鱼种实际可达的验证、完整成长路径。

### 阶段 E：验收与发行打包

完成下方清单中的功能与可靠性验证，检查手机版面、性能、暂停恢复、离线游玩和数据保留，输出签名 APK 与源码包。

产物：发行包、源码、构建文档、素材清单、验收结果、明确的剩余限制。

如某阶段缺少工具、素材调用额度、网络或设备，记录具体缺项与影响，继续完成其他不依赖它的工作。不能虚构生成图片、构建成功或设备测试结果。

## 13. 验收清单

对关键计数、结算、数据模型和存档边界进行有针对性的自动化验证；对手感、物种识别、美术、布局和设备表现进行实际检查。不要用只验证函数存在或重复实现逻辑的检查代替有效验证。

| 验收项 | 通过条件 |
| --- | --- |
| 完整游玩 | 能独立完成抛竿到成功钓获或逃脱的全过程 |
| 物种与地点 | 首版内容量达到约定范围；所有可收集鱼都有实际出现途径 |
| 大小差异 | 同种鱼有多种合理尺寸，重量有关联，拉力与展示有差别 |
| 首次发现 | 第一条该物种使图鉴解锁，发现物种数增加 1 |
| 累计计数 | 连续钓获同种鱼 3 条后显示 3；逃脱不增加；卖掉或放生后仍为 3 |
| 跨地区计数 | 同一物种在两处水域钓获，合并到同一累计统计 |
| 去重结算 | 相同 catch_id 或重复结果回调只增加一次统计、一次奖励 |
| 纪录准确 | 最大长度和最大重量分别指向实际钓获的个体 |
| 收藏展示 | 设为收藏、打开详情或展示页不会新增计数，引用信息一致 |
| 重启恢复 | 关闭并重开游戏，数量、纪录、装备、解锁与收藏保持 |
| 写入异常 | 写入失败明确提示，重试不重复发奖励；损坏存档可恢复或被保护 |
| 版本兼容 | 验证旧版迁移与新增物种，不重置既有累计数量 |
| 中断行为 | 切到后台后不继续失控溜鱼，恢复时输入正常 |
| 素材完成 | 没有缺图；鱼种可辨认；透明边缘正确；关键页面不是占位图 |
| 资源可移植 | 新环境从工程与文档能找到全部所需资源，不依赖原机器临时路径 |
| 离线游玩 | 断网后能进入全部已解锁地区、钓鱼、查看图鉴并保存 |
| 安卓安装 | 签名 APK 在记录的设备或模拟器上能够安装并启动 |
| 更新保留 | 使用相同包名和签名的新版覆盖安装后，验证原存档仍可读 |
| 移动端体验 | 安全区、触控、返回键和中文正常；记录实际设备与性能结果 |

对每项标记“通过”“失败”或“未验证”，注明验证方式。没有真机时保留相应未验证项，不用桌面鼠标操作代替安卓触控结论。

## 14. 最终交付清单

1. 完整 Godot 工程，包含静态配置、场景、脚本和实际引用素材。
2. 签名发行 APK，带版本号、文件大小和校验值；说明最低系统版本与测试设备。
3. 源码压缩包，排除签名密钥、密码、临时缓存和无关工作文件。
4. README：运行、安卓构建、安装、更新与存档位置说明。
5. 内容清单：水域、钓点、鱼种数量与对应唯一 ID。
6. 素材清单：生成提示词、参考资料、实际文件路径、许可和校对状态。
7. 简要架构与数据说明：如何增加一个鱼种、一个钓点，以及怎样保持存档兼容。
8. 验收记录：自动化、桌面、模拟器、真机分别列明结果。
9. 已知问题与后续计划：区分 V1 未完成项和后续扩展功能。

游戏包、项目源代码、美术底稿和签名私密材料应有清楚的存放边界。生成素材的提示词与实际文件必须能对应起来，方便后续继续制作。

## 15. 工作方式与完成标准

- 优先依据已经确认的需求做合理决定；普通实现细节不必反复询问用户。
- 只有关键需求冲突、新增外部付费服务、必须由用户提供的访问条件或会改变交付范围的取舍，才需要说明原因并询问。
- 不主动发布到应用商店、公开托管素材或发送给第三方；此类发布另行取得用户授权。
- 修改现有项目时遵守其适用指令，保留用户工作，不覆盖不相关文件。
- 对当前工具或环境做真实检查，不假定有生图能力、Godot、安卓 SDK 或连接的手机。
- 保留必要的开发进度与下一步说明，任务中断后能够从现有工程继续。
- 按阶段报告具体成果、验证方式和剩余问题；不把内容规划写成已经实现。

**最终目标：玩家在安卓手机上打开游戏，能去多个地区钓到外形与行为有区别、大小不同的真实鱼种；图鉴准确展示发现进度、每种鱼累计钓获数量与个人尺寸纪录，并在重启和正常版本更新后保留这些数据。**
